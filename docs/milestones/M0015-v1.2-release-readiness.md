## Goal

Produce a release-ready YADG 1.2.0 package whose installed consumer surface includes M0014 text diagrams without regressing the 1.1 authoring/rendering contract, and whose public documentation clearly separates:

1. Markdown/source authoring; and
2. DOCX template authoring.

The Markdown guide must make the two supported diagramming approaches understandable as distinct choices:

```text
built-in text-grid diagrams -> source-grid geometry -> internal SVG -> DOCX
Mermaid diagrams            -> Mermaid source -> configured external producer -> PNG -> DOCX
```

### Markdown authoring guide

`docs/user/MARKDOWN-AUTHORING.md` is the canonical source-authoring guide.

It must cover at least:

- source/workspace structure relevant to Markdown authors;
- stable IDs and semantic references;
- sections/content hierarchy;
- paragraphs/inlines;
- flat lists;
- tables;
- PNG/JPEG figures;
- captions/reference relationship at an author-facing level;
- Markdown policy (`thematicBreak`, `codeInline`);
- explicit built-in `diagram` fences;
- supported text-diagram primitive scope;
- whitespace/source-grid geometry;

- anonymous detected diagrams versus identified figures;
- Mermaid fence syntax and external producer requirement;
- a concise “Text diagram or Mermaid?” comparison;
- strict/YOLO implications relevant to source authoring.

The comparison must not imply that text diagrams and Mermaid are interchangeable implementations. Text diagrams are built-in and source-grid positioned; Mermaid is an external semantic diagram language rendered by a configured producer.

### DOCX template authoring guide

`docs/user/DOCX-TEMPLATE-AUTHORING.md` is the canonical prepared-template guide.

It must cover at least:

- template ownership boundary;
- ordinary visible text tags rather than content controls;
- `section`, `content`, `table`, `figure`, and `value` placement tags;
- template front matter;
- presentation-resolution principle;
- `inspect styles` and `inspect template`;
- heading composition;
- list styles and list-item prototypes;
- caption prototypes/SEQ/REF requirements;
- prepared table rows and `{{cell}}`;
- inline-code character style;
- value substitution and formatting inheritance;
- TOC/index/field ownership at an author-facing level;
- YOLO presentation fallbacks;
- human-searchable Word diagnostics;
- what belongs in the template versus Markdown.

The guide should explicitly state that text diagrams and Mermaid both arrive at the template as figure-like content; templates place identified diagrams through the existing `{{figure:id}}` mechanism and do not define diagram geometry.

### Renderer verbose diagnostics

M0015 adds an invocation-local diagnostic mode for render troubleshooting:

```text
yadg render --verbose
```

`--verbose` is diagnostic output, not persistent logging configuration. Normal render output remains unchanged when the option is absent. Diagnostic output must go to stderr so ordinary command output remains usable.

For LibreOffice, verbose output must expose enough phase timing to identify where a small-document timeout is occurring. At minimum distinguish:

```text
runtime/executable resolution
version/runtime discovery
isolated session/process start
per-document package normalization
UNO connect
document load
field refresh
index update
link update
calculation
DOCX save
PDF export
document close
output validation/commit
cleanup
```

Unsupported/no-op phases may be omitted, but the trace must make the current phase and completed phase durations unambiguous. Per-document and total elapsed time must be reported. Process/session identity may be reported when useful, but diagnostics must not dump environment variables, credentials, document contents, or other unrelated sensitive state.

The LibreOffice sidecar/process protocol must report progress while work is executing so that a timeout can identify the last completed/current phase. Redirected child stdout/stderr must be consumed concurrently while the process runs; enabling verbose diagnostics must not introduce pipe-buffer deadlocks or new hangs.

When the existing LibreOffice operation timeout fires, the normal actionable diagnostic must additionally identify at least:

- configured timeout duration;
- input document;
- elapsed time;
- current or last observed phase.

The current 30-second timeout is not to be increased merely to make M0015 validation pass. These release fixtures are intentionally small; a timeout is therefore treated first as evidence of a stall, startup/connectivity problem, process-I/O problem, or unexpectedly slow specific UNO phase. If verbose evidence shows that otherwise healthy representative small-document work legitimately exceeds 30 seconds, return to planning before changing the product timeout policy.

Word may emit only common renderer-level timings in M0015; detailed Word object-model tracing is not required. This milestone does not introduce a general logging framework or persistent log files.
