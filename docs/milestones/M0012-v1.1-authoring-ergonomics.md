## Goal

Complete the author-facing model that the first M0012 implementation only partially captured.

YADG is template-first: presentation must be resolved from template examples/resources, not primarily from hidden Word style IDs.

YADG is also an authoring tool: strict validation remains essential, but an author may explicitly ask YADG to produce the best useful artifact it safely can while template/runtime problems are being fixed.

This correction adds:

1. a generalized template-presentation/example model;
2. `yadg inspect template`;
3. human-searchable Word diagnostic locations;
4. explicit, noisy, deterministic YOLO recovery;
5. cross-renderer YOLO fallback;
6. versioned built-in fallback examples.

## Core principles

### Discoverability

Anything YADG expects an author to configure must be discoverable through YADG.

### Template examples are the product model

Placement paragraphs, caption prototypes, prepared-table prototype rows, list prototypes, style roles, numbering, and placeholder run formatting are mechanisms under one common presentation model.

Styles are one mechanism, not the conceptual center.

### Strict by default; permissive only on demand

Normal behavior remains strict.

YOLO is enabled only by explicit CLI `--yolo` for that invocation. It is not persisted in `YADG.md`.

### YOLO may degrade; it may not lie

YOLO may choose a deterministic related template resource, use a built-in fallback example, remove optional presentation, preserve unresolved tokens visibly, or substitute an alternate supported renderer.

YOLO must not guess through ambiguous semantic identity, bypass path/security rules, silently drop meaningful content, call an unfinalized PreWord finalized, or claim one renderer was used when another actually produced the artifact.

Every recovery is a visible degradation diagnostic.

## Scope additions

### Template presentation resolution

Implement the common role/example/fallback model in `TEMPLATE-PRESENTATION.md`.

At minimum cover:

- ordinary/contextual paragraphs;
- headings;
- unordered/ordered list items;
- generated tables;
- prepared table rows;
- figure/table captions;
- inline code;
- value replacement formatting.

Strict mode keeps template ownership and compatibility.

YOLO may additionally use related template resources and built-in fallback examples where the role contract permits.

### Inspect template

Add:

```text
yadg inspect template [--workspace <path>] [--template <filename.docx>]
```

`inspect styles` answers which serialized styles exist.

`inspect template` answers what YADG understands about the template and how its presentation roles resolve.

It reports at least:

- front-matter/control-region presence;
- placement tags and human-searchable locations;
- prototypes and bound roles;
- configured style selectors and resolved style name/ID/type;
- strict role-resolution status;
- YOLO candidate/fallback preview when strict resolution fails;
- relevant structural authoring warnings.

It works even when ordinary `check` fails for unrelated Markdown/producer reasons and does not execute external producers.

### Human-searchable DOCX diagnostics

A diagnostic must not rely on `paragraph 16` as the sole human locator.

Where available, show:

1. relative DOCX path;
2. story/container;
3. nearest prepared-template heading context/path;
4. bounded normalized nearby text that can be pasted into Word Find;
5. paragraph/table/prototype ordinal as supplemental structure.

Example:

```text
YadgTemplates/report.docx
body > "Operational Risks" > paragraph 27
near: "Availability of the upstream system"
```

Machine identifiers such as package part or `w14:paraId` may be retained secondarily.

### YOLO CLI

Add:

```text
yadg check --yolo
yadg build --yolo
yadg render --yolo
```

Strict remains default.

`init`, `inspect styles`, and `inspect template` do not need YOLO.

`publish` remains finalized-DOCX-only and does not fall back to `YadgPreWords`.

### Degradation diagnostics

Introduce a visible non-fatal degradation category, e.g.:

```text
degradation YADG-YOLO-... <location>: <problem>; fallback: <selected recovery>
```

Every recovery identifies the original problem and selected fallback.

Successful YOLO commands print a degradation count.

### Renderer fallback

`render --yolo` may fall back:

```text
word -> libreoffice
libreoffice -> word
```

Use the normal supported renderer contracts only.

Preserve staging/commit safety; do not merge partial output from two renderer runs.

On fallback success, clearly report requested and actual renderer.

If both renderers fail, render fails and PreWords remain authored intermediates only.

### Built-in fallback examples

YOLO may use versioned implementation-owned fallback examples.

At minimum:

```text
builtin:plain-v1
builtin:unordered-list-v1
builtin:ordered-list-v1
```

Storage is implementation-owned.

Built-ins are never used in strict mode and must be visible through `inspect template` when selected.

For list fallback, YOLO may create the minimal real Word numbering structures needed by the built-in list example. This explicitly supersedes the earlier blanket ban on synthesized numbering only for YOLO fallback.

## Recoverable YOLO cases

When a defined safe fallback exists, at minimum recover:

- missing/unusable presentation style;
- missing/unusable list numbering;
- missing optional list prototype;
- missing inline-code character style;
- thematic break;
- inline code presentation;
- failed Mermaid producer via obvious visible placeholder;
- missing/unreadable in-workspace figure asset via obvious visible placeholder;
- unresolved workspace value by preserving visible `{{value:id}}`;
- unresolved semantic reference by preserving a visible `[@id]`-equivalent marker;
- one unreadable template when other templates can still produce useful output;
- requested renderer failure when alternate renderer succeeds.

## Fatal even in YOLO

At minimum:

- malformed `YADG.md` that cannot be interpreted reliably;
- duplicate/ambiguous semantic identity requiring a guess;
- path traversal/security-boundary violations;
- unsafe/corrupt DOCX state preventing safe handling;
- inability to produce any requested useful artifact;
- both supported renderers failing;
- unsafe publication destination;
- any recovery that would fabricate semantic content or falsely claim an operation happened.

For multiple templates, YOLO may skip a recoverable failed template and continue. If no requested artifact is produced, the command fails.

## Deterministic fallback selection

Fallback selection is deterministic for identical inputs and YADG version.

Only type/capability-compatible candidates qualify.

Role capability outranks names.

Examples:

- unordered list: usable bullet numbering;
- ordered list: usable non-bullet numbering;
- heading: matching effective outline level;
- table: concrete table style;
- inline code: character style with strong code/source/monospace hint; otherwise plain text, not arbitrary style.

Within equal candidates, order by normalized visible name then internal ID.

Strict selector resolution remains exact ID/name/alias. Heuristic/related matching is YOLO-only.

## Acceptance additions

### Presentation model

- `TEMPLATE-PRESENTATION.md` is active project authority.
- existing caption/list/prepared-table/contextual examples are documented as one mechanism;
- strict and YOLO role resolution are explicit;
- `TEMPLATE-STYLES.md` is reconciled so styles are a mechanism, not the product model.

### Inspect template

- command exists, documented and help-covered;
- lists placements/prototypes/bindings and role resolution;
- shows strict failure plus YOLO candidate/built-in preview;
- includes human-searchable locations;
- deterministic;
- independent of unrelated Markdown/producer validity.

### Human Word locations

- body, footer, prototype, and supported text-container diagnostics include searchable nearby text where available;
- heading context is included where available;
- paragraph ordinal is supplemental;
- excerpts are bounded/whitespace-normalized.

### YOLO check/build

- strict still fails the paired case;
- YOLO succeeds only after explicit recovery and emits degradation;
- missing `ListBullet` no longer blocks YOLO build if related list presentation or built-in fallback exists;
- no-list-resource case uses real built-in numbering;
- inline code falls back to related character style or plain text;
- thematic break may be omitted;
- missing values/references remain visibly unresolved rather than invented;
- producer/asset failure yields an obvious placeholder;
- no-output case still fails.

### YOLO renderer

- strict requested-renderer failure still fails;
- `render --yolo` tries the alternate supported renderer;
- success reports requested and actual renderer/runtime;
- primary failure remains visible as degradation context;
- both-failed case fails and does not place PreWords into `YadgWords`.

### Publication boundary

- alternate-renderer finalized output is publishable normally;
- `publish` never falls back to PreWords;
- docs preserve the meaning of authored vs finalized artifacts.

### Safety boundary

Focused tests prove YOLO does not guess through duplicate IDs, malformed config, or path/security violations.

## Escalation boundary

Return to planning if:

- built-in list fallback cannot remain structurally valid in both Word and LibreOffice;
- cross-renderer retry cannot preserve staged-output safety;
- a proposed fallback requires choosing between ambiguous semantic identities;
- preserving content would require changing semantic meaning;

Do not turn YOLO into `catch { }` and do not hide diagnostics.
