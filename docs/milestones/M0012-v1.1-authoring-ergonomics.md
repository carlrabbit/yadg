## Goal

Make YADG 1.1 materially easier to author with and troubleshoot without requiring users to understand Markdig implementation classes, absolute workspace paths, raw Word style IDs, or WordprocessingML numbering internals.

The milestone addresses the concrete 1.0 authoring friction discovered after release:

- insufficient authoring documentation;
- no workspace bootstrap command;
- no controlled policy for common unsupported Markdown constructs such as thematic breaks and inline code;
- diagnostics lacking useful source position/compact workspace-relative paths;
- `check` not exposing the discovered workspace inventory;
- Word style/list errors that are difficult to understand or escape;
- no command to discover usable Word styles/names/aliases;
- list formatting that assumes a paragraph-style/numbering shape users may not be able to create or inspect in Word;
- repository operational artifacts/ledgers/review state tracked as product content;
- `docs/SPECS.md` acting as a partial competing summary rather than a specification index;
- stale post-release bookkeeping that still described 1.0 as unreleased/ready.

## Target state

A new or existing author can:

```text
yadg init
yadg check --list
yadg inspect styles
```

and use those commands plus dedicated user documentation to understand:

- the workspace structure;
- source/template/reference discovery;
- exact Markdown error locations;
- template style names and aliases visible in Word;
- internal style IDs only when needed for disambiguation;
- whether a paragraph style is list-capable;
- how to use a real list paragraph prototype when Word's list/style model is opaque;
- how inline code/thematic breaks are handled.

The current product tree no longer tracks `.execution/`, `.review/`, or generated `artifacts/`.

## Scope

### Workspace bootstrap

Add:

```text
yadg init [--workspace <path>]
```

with the exact safety and generated starter contract in `docs/specs/AUTHORING-EXPERIENCE.md`.

### Markdown authoring policies

Extend `YADG.md` schema-v1 with:

```yaml
markdown:
  thematicBreak: error | ignore
  codeInline: error | ignore | style
```

Defaults remain `error`.

`codeInline: ignore` preserves code text as ordinary text.

`codeInline: style` uses a template-owned character-style role.

### Diagnostics

Improve human diagnostics with:

- workspace-relative paths;
- 1-based Markdown/YAML line/column where a concrete textual token/node exists;
- structural DOCX locations rather than fake line numbers;
- visible warnings as well as errors;
- unchanged error/non-error exit semantics.

### Check discovery

Keep the compact count summary and correct its reference count to mean all referenceable semantic objects.

Add:

```text
yadg check --list
```

for deterministic sources/templates/reference inventory.

### Template/style introspection

Add:

```text
yadg inspect styles [--workspace <path>] [--template <filename.docx>]
```

with the style metadata/numbering visibility defined by `docs/specs/TEMPLATE-STYLES.md`.

This command must remain useful even when normal `check` is failing because of style/list configuration.

### Style binding overhaul

Template style selectors support:

- exact style ID;
- primary Word UI name;
- Word aliases.

Resolution, ambiguity handling, and role type constraints are fixed by `docs/specs/TEMPLATE-STYLES.md`.

Existing valid 1.0 style-ID configuration remains compatible.

### List escape hatch

Support template-owned list item prototypes:

```text
prototypes.unorderedListItem
prototypes.orderedListItem
```

using a real Word list paragraph containing exactly one `{{item}}`.

When configured, the prototype is authoritative for that list kind and removes the requirement that the user discover/create a separately usable list paragraph style.

Improve style-based numbering discovery so a style is not rejected merely because it lacks direct `numPr` when Word's numbering definitions associate the style through normal WordprocessingML relationships.

### Inline code style

Add template role:

```text
codeInline
```

requiring a character style when selected workspace content uses `markdown.codeInline: style`.

## Resolved decisions and constraints

### 1. User-facing configuration does not expose parser class names

The public YAML keys are:

```text
thematicBreak
codeInline
```

not:

```text
ThematicBreakBlock
CodeInline
```

This prevents Markdig implementation types from becoming persisted YADG configuration API.

### 2. 1.0 unsupported behavior remains the default

Both new Markdown policies default to:

```text
error
```

Existing workspaces do not silently lose/change content merely by upgrading to 1.1.

### 3. Ignoring inline code means ignoring presentation, not text

`codeInline: ignore` emits the code span's content as ordinary text.

Dropping inline code content is forbidden.

### 4. Presentation remains template-owned

Workspace YAML selects the semantic policy (`style` vs `ignore`).

The concrete Word character style for inline code belongs in template front matter.

### 5. Word UI names and aliases are first-class selectors

Users may configure the style name they see in Word.

Internal style IDs remain supported for backward compatibility and precise disambiguation.

No fuzzy matching.

### 6. Style types are enforced

Paragraph/table/character role mismatches are errors rather than silently applying an inappropriate style.

### 7. List prototypes are the explicit escape hatch

YADG will not force users to reverse-engineer a hidden or inaccessible list style.

A real list paragraph in a template prototype can own numbering, indentation, paragraph/run presentation, and is cloned for semantic list items.

### 8. Existing style-based lists remain supported

Valid 1.0 templates do not have to migrate to prototypes.

Numbering validation becomes more faithful to Word's actual style/numbering relationships.

### 9. Diagnostics are workspace-oriented

Workspace paths are relative.

Text nodes get real source line/column.

DOCX locations get Word-structural locators rather than fictional lines.

### 10. `check --list` is human-readable

No JSON/stable serialization contract is introduced in M0012.

### 11. `inspect styles` bypasses unrelated workspace validity

The command inspects concrete DOCX template styles even when Markdown/config/producer validation would make ordinary `check` fail.

It does not execute Mermaid producers.

### 12. `init` never overwrites

No `--force` exists in M0012.

Preflight failure occurs before partial scaffold creation.

### 13. Operational guide state is local, not product content

`.execution`, `.review`, and `artifacts` remain usable locally but are ignored/untracked on the normal product branch.

This changes repository hygiene, not the guide's conceptual execution/review process.

### 14. M0012 is not 1.1 release-readiness

A later release-readiness/publication task may version/package/publish 1.1 after the feature line is accepted.

## Acceptance criteria

### Init

- `yadg init` and `--workspace` work as specified.
- missing target directory can be created.
- unrelated existing files do not prevent initialization.
- any conflict with an owned bootstrap path causes preflight failure and zero partial bootstrap mutation.
- generated scaffold has valid `YADG.md`, starter `content.md`, and `YadgTemplates/`.
- no DOCX or generated output directory is synthesized.
- success output states the next template/check step.
- ordinary `check` does not warn merely because generated output directories are absent.

### Markdown policies

- schema-v1 accepts the new `markdown` mapping.
- unknown keys/modes fail.
- omitted settings preserve 1.0 error behavior.
- thematic break `ignore` removes the break without diagnostic/output.
- code inline `ignore` preserves text as ordinary text.
- code inline `style` preserves a distinct semantic inline until template authoring.
- ordinary unsupported fenced code blocks remain errors.

### Style selector behavior

- existing exact style IDs keep working.
- primary UI names resolve.
- aliases resolve.
- matching is case-insensitive for names/aliases and exact ordinal for ID precedence.
- ambiguity produces an actionable error with candidate IDs/names.
- wrong style type produces an actionable error.
- no fuzzy/substring resolution exists.

### Inspect styles

- works against invalid-for-other-reasons workspaces/templates where the DOCX itself is readable.
- does not run content producers.
- lists all concrete style types and required metadata.
- reports name, ID, aliases, visibility flags when present.
- reports useful paragraph numbering capability/source.
- multiple templates are grouped/deterministically ordered.
- `--template` cannot escape top-level `YadgTemplates`.
- diagnostics direct users to this command when style resolution fails.

### Lists

- existing valid style-based unordered/ordered lists continue to build.
- numbering association through supported Word style/numbering relationships is recognized.
- genuinely unusable/ambiguous numbering fails with actionable diagnostics.
- unordered/ordered list prototypes validate exactly one paragraph + `{{item}}` + effective numbering.
- list prototype binding takes precedence over list style binding for that kind.
- cloned items preserve prototype paragraph/numbering/formatting and render Markdown inline content/references correctly.
- ordered prototype clones continue as intended numbering sequence.
- no literal fake bullet/number glyph is synthesized as a substitute for Word numbering.

### Inline-code style

- `codeInline` template role requires character style.
- selected rendered inline code receives that character style only.
- surrounding paragraph presentation is preserved.
- `codeInline: ignore` needs no template code style.
- templates not rendering styled inline code do not fail merely because no `codeInline` role exists.

### Diagnostics

- workspace-owned diagnostic paths are relative.
- Markdown/YADG.md token diagnostics carry 1-based line/column where available.
- DOCX diagnostics use relative path plus useful story/paragraph/prototype structural location where available.
- warnings are shown.
- exit status fails only for errors.
- existing diagnostic codes remain recognizable.

### Check listing

- compact summary still prints counts.
- reference count includes sections + tables + figures.
- `--list` prints relative source/template paths and typed stable references.
- order is deterministic.
- listing remains useful with partially invalid discovered workspaces.
- output is documented as human-readable, not a stable machine serialization.

### Documentation

- all four required `docs/user/` documents exist and satisfy `AUTHORING-EXPERIENCE.md`.
- README links the user docs and remains concise.
- actual CLI examples/help and docs agree.
- list-style troubleshooting explains ID/name/aliases and prototypes.
- users are not instructed to inspect/edit raw OOXML to configure ordinary styles.

### Repository/spec hygiene

- `.gitignore` ignores `.execution/`, `.review/`, and `artifacts/`.
- `git ls-files` reports no tracked files below those paths after implementation.
- M0012 local execution ledger still exists/works during implementation even though ignored.
- review tooling remains functional with local ignored `.review` when exercised by its tests.
- committed realistic Office fixtures remain tracked.
- `docs/SPECS.md` links every active focused spec and no longer contains stale competing partial contracts.
- M0011/release/changelog bookkeeping reflects released 1.0 and current post-1.0 development.

- performing or packaging 1.1 release publication.
